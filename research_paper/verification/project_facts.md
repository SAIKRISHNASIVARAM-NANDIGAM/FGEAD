## Dataset

### Primary Dataset: Server Machine Dataset (SMD)
- **Dataset name:** Server Machine Dataset (SMD)
- **Dataset source:** Real-world server monitoring data from OmniAnomaly (Su et al., 2019); data files located in `data/SMD/`
- **Number of machines:** 28 machines across 3 server clusters (machine-1-1 through machine-3-11)
- **Evaluated machine:** machine-1-1
- **Number of features:** 38 (per machine)
- **Feature names:** Generic telemetry features labeled `feature_00` through `feature_37` (SMD does not publish semantic feature names; the features represent server metrics such as CPU, memory, disk, and network utilization)
- **Target variable:** Binary anomaly label (0 = normal, 1 = anomaly)
- **Classes:** 2 (Normal, Anomaly)
- **Train timesteps (machine-1-1):** 28,479
- **Test timesteps (machine-1-1):** 28,479
- **Train windows:** 5,684
- **Test windows:** 5,684
- **Test anomaly windows:** 635
- **Test anomaly points:** 2,694
- **Missing values:** Handled via forward-fill and backward-fill
- **Class distribution:** Anomaly rate approximately 9.46% at the point level for machine-1-1

### Secondary Dataset: Synthetic Dataset
- **Dataset name:** Synthetic server telemetry data
- **Generated by:** `data/synthetic_generator.py`
- **Number of samples:** 5,000 timesteps
- **Number of features:** 20
- **Feature names:** `cpu_usage`, `memory_usage`, `net_in`, `load_avg_1m`, `cpu_temp`, `memory_free`, `disk_io_read`, `disk_io_write`, `net_out`, `net_packets`, `swap_usage`, `disk_usage`, `process_count`, `thread_count`, `context_switches`, `interrupts`, `page_faults`, `cache_hit_ratio`, `io_wait`, `system_load`
- **Target variable:** Binary `label` column (0 = normal, 1 = anomaly)
- **Anomaly rate:** ~5%
- **Anomaly types injected:** Spikes (4–6σ jump), correlation breaks, gradual drifts
- **Built-in correlations:** `cpu_usage` & `cpu_temp` (positive 0.85), `memory_usage` & `memory_free` (inverse −0.90)
- **Temporal patterns:** Diurnal (1440 min) and weekly (10080 min) sine wave cycles

## Preprocessing

- **Missing-value handling:** Forward-fill (`df.ffill()`) then backward-fill (`df.bfill()`)
- **Duplicate handling:** Exact duplicate rows dropped
- **Encoding:** Not applicable (all features are continuous numerical)
- **Normalization/Standardization:** `sklearn.preprocessing.StandardScaler` — fitted ONLY on training data to prevent data leakage; test data transformed using training statistics
- **Scaling:** Z-score standardization (zero mean, unit variance)
- **Outlier handling:** Not explicitly applied as a preprocessing step; the model itself is trained to detect outliers
- **Feature selection:** No explicit feature selection; all features are used
- **Feature engineering:** Sliding window construction — window size 60, stride 5 (chronological, no shuffling)
- **Train/test split:** Chronological split (first half train, second half test, as per SMD convention)
- **Validation procedure:** 15% of training windows used for calibration/validation

## Machine Learning

### Model: FGEAD (Feature-level Graph-based Explainable Anomaly Detection)

**Architecture (4 modules):**

1. **Feature Embedding (GraphLearner)**
   - `nn.Embedding(n_features, embed_dim=64)` — learnable feature embeddings
   - Input values scaled into embedding space
   - `nn.LayerNorm(64)` + `nn.Dropout(0.1)`
   - Output: `(Batch, Time, Features, 64)`

2. **Self-Attention Graph Learner (GraphLearner)**
   - Temporal pooling via `mean(dim=1)`
   - Q, K, V linear projections: `nn.Linear(64, 64, bias=False)`
   - 4-head self-attention
   - Top-K sparsification (k=5 connections per feature)
   - L1 sparsity regularization on adjacency weights
   - Residual connection back to embeddings
   - Output: Dynamic adjacency matrix + enriched feature embeddings

3. **Temporal GCN + LSTM (TemporalGCN)**
   - **Graph Convolution:** Row-normalized adjacency matrix multiplication, `nn.Linear(64, 64, bias=False)`, ReLU, `nn.BatchNorm1d(64)`
   - **LSTM:** 2-layer `nn.LSTM`, hidden_size=128, dropout=0.2, batch_first=True
   - Input to LSTM: flattened GCN output `(B, T, Features × 64)`

4. **Forecasting Head + Anomaly Scoring (FGEAD)**
   - 2-layer MLP: `nn.Linear(128, 64)` → ReLU → Dropout(0.2) → `nn.Linear(64, n_features)`
   - Learned feature score weights: `nn.Parameter(torch.ones(n_features) / n_features)` normalized via Softmax
   - Anomaly score = weighted sum of per-feature absolute forecast errors

**Training Procedure:**
- **Paradigm:** Semi-supervised (trained on normal data only)
- **Task:** Next-timestep forecasting
- **Loss function:** `MSELoss(predictions, actuals) + sparsity_loss`
- **Optimizer:** Adam (lr=1e-3, weight_decay=1e-4)
- **Scheduler:** ReduceLROnPlateau (factor=0.5, patience=5 for synthetic / patience=3 for SMD)
- **Batch size:** 64
- **Epochs:** 50 (synthetic) / 30 (SMD)
- **Gradient clipping:** max_norm=1.0
- **Early stopping:** patience=10 (synthetic) / patience=7 (SMD)
- **Random seed:** [INFORMATION REQUIRED — not explicitly confirmed in code analysis]

**Libraries:**
- PyTorch >= 2.0.0
- NumPy >= 1.24
- pandas >= 2.0
- scikit-learn >= 1.3

**Model serialization:**
- `checkpoints/best_model.pt` (synthetic)
- `checkpoints/fgead_smd_machine_1_1.pt` (SMD)
- Training history saved as `.npy` files

**Anomaly Detection Method:**
- Forecasting-based: model predicts next timestep from input sequence
- Absolute prediction error: `|actual - predicted|` computed per feature per timestep
- Errors weighted by learned feature score weights and summed to produce scalar anomaly score
- Threshold calibrated from normal training data (99.5th percentile) or by maximizing F1 on validation set

## Explainable AI

### XAI Technique: Custom Post-Hoc Deviation-Based Feature Attribution + Graph Relationship Auditing

**NOT SHAP. NOT LIME.** The project implements a custom, domain-specific explainability framework.

### 5-Question Framework (from `models/explainer.py`):

**Q1 — Which features deviated most?**
- `FeatureDeviationAnalyzer` class
- Calculates absolute deviation `|actual - predicted|` at the peak anomaly timestep
- Deviations standardized into Z-scores: `z = deviation / window_std`
- Features ranked by deviation magnitude
- Top-K features reported (default k=5)

**Q2 — What did they deviate from?**
- Reports actual values vs. predicted values for each top feature
- Values inverse-transformed to original data scale for interpretability
- Direction labeled: `"↑ spike"` (actual > predicted), `"↓ drop"` (actual < predicted), `"≈ stable"`

**Q3 — Which feature relationships changed?**
- `GraphRelationshipAuditor` class
- Computes Pearson correlation matrix of the anomalous window (peak ±10 steps)
- Compares observed correlation against model's learned attention weights (expected dependency)
- Flags relationships where `|observed − expected| >= 0.20`
- Break types:
  - `"COMPLETE DECOUPLING"`: expected ≥ 0.70 but observed < 0.10
  - `"SIGN REVERSAL"`: expected ≥ 0.20 but observed < 0
  - `"RELATIONSHIP CHANGE"`: generic gap ≥ 0.20
- Severity levels: CRITICAL (gap ≥ 0.70), HIGH (gap ≥ 0.50), MEDIUM (gap ≥ 0.20)

**Q4 — When did the anomaly start and end?**
- Temporal range detection: identifies contiguous anomalous timesteps
- Reports start, end, duration in steps, and percentage of window affected

**Q5 — How confident is the alert?**
- Composite confidence score:
  - Peak anomaly score: 40% weight
  - Duration: 25% weight
  - Top features affected: 20% weight
  - Graph pairs broken: 15% weight
- Alert levels: CRITICAL (≥80%), HIGH (≥60%), MEDIUM (≥40%), LOW (<40%)

### Root Cause Generation:
- Keyword matching on top feature names to generate domain-specific diagnostic phrases
- Example: if `"cpu"` and `"mem"` flagged → `"Likely CPU and memory pressure event"`
- For generic features: `"Unusual multivariate pattern detected: feature_33 ↑ spike, feature_28 ↑ spike, ..."`

## Backend

- **Framework:** FastAPI >= 0.103
- **Server:** Uvicorn >= 0.23

### API Endpoints:
| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/health` | GET | System health check — model loaded status, device, machine ID, features, window size, stride |
| `/dataset` | GET | Dataset statistics — machine, timesteps, features, anomaly rate, window counts |
| `/machine` | GET | Machine characteristics — machine ID, feature count, feature names |
| `/predict` | POST | Inference + XAI — accepts 60×38 window data, returns prediction, anomaly score, threshold, confidence, alert level, top features, broken pairs, root cause |

### Request Format (`/predict`):
```json
{
  "data": [[...], ...],  // 60×38 float matrix
  "window_start_abs": 17485
```

## Frontend

- **Framework:** Streamlit >= 1.27
- **Design:** Enterprise observability dashboard (Datadog/Grafana aesthetic)

### Pages/Components:
1. **Overview** — Summary statistics (total windows, features, anomalies, anomaly rate)
2. **Anomaly Detection** — Interactive Plotly telemetry timeline with ground-truth anomaly regions shaded; window selector
3. **Explainability** — Alert banners (CRITICAL/HIGH/MEDIUM/LOW); top contributing features table with progress bars; actual vs. forecast profile charts
4. **Feature Graph** — Visualization of changed feature relationships
5. **Timeline** — Temporal anomaly range analysis
6. **Model Performance** — Evaluation metrics display
7. **System Health** — Backend status monitoring

### Visualizations:
- **Telemetry Timeline Explorer:** Downsampled time-series with red anomaly shading and blue selected-window overlay (Plotly)
- **Top Contributing Features:** HTML table with visual severity bars, Z-scores, direction indicators
- **Actual vs. Forecast Profile:** Side-by-side Plotly time-series comparison
- **Changed Relationships Table:** Expected vs. observed correlation, gap severity, break type
- **Alert Banners:** Color-coded (CRITICAL=red, HIGH=orange, MEDIUM=yellow, LOW=green)

### API Communication:
- Streamlit app communicates with FastAPI backend via HTTP requests
- JSON data exchange
